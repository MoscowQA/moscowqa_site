# CLAUDE.md

Инструкции для Claude Code при работе в этом репозитории.

## Что это за проект

Статический сайт сообщества Moscow QA. Генератор — `build.py` (Python, Jinja2 + markdown), читает контент из `content/` и рендерит HTML в `dist/`.

```bash
make install           # зависимости
make build             # собрать сайт в dist/
make serve             # собрать и открыть на http://127.0.0.1:8000
make test              # тесты (нужен make install-dev)
make validate          # проверить контент и внутренние ссылки
make                   # список всех целей
```

`make` — просто обёртка: `python3 build.py` и остальные скрипты по-прежнему
работают напрямую.

## Структура контента

- `content/events/{номер}-{слаг}.md` — митапы. Правила добавления/обновления — см. [`EVENT_GUIDE.md`](./EVENT_GUIDE.md).
- `content/speakers/{имя-фамилия}.md` — профили спикеров. Правила — см. [`SPEAKER_GUIDE.md`](./SPEAKER_GUIDE.md).
- `templates/` — Jinja2-шаблоны страниц.
- `static/images/speakers/` — фото спикеров.

## Ключевые правила

- **Связь докладов со спикерами — по точному совпадению имени.** Значение в `talks[].speakers` в файле события должно дословно совпадать с полем `name` в `content/speakers/*.md`. Иначе доклад не свяжется с профилем.
- **Новый спикер → обязательно прогнать синхронизацию с конференциями.** Если для события создан новый файл в `content/speakers/`, сразу выполните:
  ```bash
  make sync
  ```
  Это подтягивает прошлые доклады спикера с SQA Days и Heisenbug в `external_talks`. Для уже существующих спикеров повторный прогон не обязателен.
- **Темы докладов — из готового списка.** Поле `tags` в `talks[]` собирает страницы `/tags/{тема}/`. Берите теги из тех, что уже используются (список — в [`EVENT_GUIDE.md`](./EVENT_GUIDE.md)), новый заводите, только если доклад правда не попадает ни в одну тему.
- **Виджет Timepad подключается сам.** Если `registration_link` события ведёт на Timepad, кнопка «Зарегистрироваться» открывает форму регистрации поверх страницы — и на странице события, и на карточках в списках. ID вытаскивается из ссылки автоматически. Управляется полем `timepad_widget` (`popup` / `inline` / `false`), подробности — в [`TIMEPAD_WIDGET.md`](./TIMEPAD_WIDGET.md).
- **Поиск по спикерам работает сам.** На `/speakers/` есть строка поиска (`static/js/speakers-search.js`): она фильтрует карточки по имени, компании, латинской транслитерации имени (слаг файла) и названиям докладов — как митапов Moscow QA, так и `external_talks`. Индекс собирается в `build.py` (`speaker_search_text`), поэтому новый спикер попадает в поиск автоматически, ничего дописывать не нужно. Запрос отражается в `?q=` — ссылкой на результат можно поделиться. Без JS страница показывает полный список, как раньше.
- **Прошедшее/предстоящее считается на сборке.** Поля `completed` в front
  matter нет: `build.py` сравнивает `date` с московским «сегодня» и
  раскладывает события по спискам (`split_events`). Главная открывается
  блоком «Ближайший митап» — это первое предстоящее событие, а если впереди
  ничего нет, тот же блок показывает последний прошедший. Чтобы разбивка не
  застывала между деплоями, сайт пересобирается каждую ночь
  (`.github/workflows/deploy.yml`), а `static/js/events-status.js` поправляет
  статус на дату самого посетителя.
- **Картинка превью для ссылок рисуется сама.** У каждого события есть
  `og:image` — карточка 1200×630 с номером, датой, названием, площадкой и
  спикерами. Её собирает `og_images.py` на сборке из front matter, поэтому
  новому событию ничего дописывать не нужно. Посмотреть, не пересобирая
  сайт: `make og` (или `make og ARGS="28-black"` для одного события).
  Если у события заполнен `cover`, в превью идёт он. Подробности — в
  [`EVENT_GUIDE.md`](./EVENT_GUIDE.md).
- **Новая обложка события → прогнать `make covers`.** Если у события
  заполнен `cover` (или `cover_desktop`), после добавления картинки выполните:
  ```bash
  make covers                  # все обложки
  make covers ARGS="28-black"  # только одно событие
  ```
  Рядом с исходным JPEG появятся webp-варианты на 540/768px и в полный размер,
  из них сборка соберёт `<picture>`. Исходник при этом остаётся на месте — он
  уходит в og:image, куда webp кладут не все соцсети. `make validate` ругнётся
  замечанием, если варианты забыли собрать.
- **Фото спикеров лежат у нас.** В `static/images/speakers/` для каждого спикера два webp: `{слаг}.webp` (~1080px) и `{слаг}-540.webp`; из них сборка собирает `srcset`. Внешние ссылки в `photo` не оставляем — если прислали URL, прогоните:
  ```bash
  make photos ARGS="ivan-ivanov"     # скачает, сожмёт и перепишет photo
  make photos ARGS=--dry-run         # посмотреть, что изменится
  ```
  Отдельный файл можно сжать и вручную: `make photo FILE=static/images/speakers/photo.png`.
- После любых правок контента запускайте `make build` и убедитесь, что сборка проходит без ошибок (проверьте счётчики событий/докладов/спикеров и тегов в выводе). `make check` дополнительно проверяет синтаксис Python и что `dist/` не пустой, а `make validate` — обязательные поля, совпадение имён спикеров, наличие картинок и внутренние ссылки. Логику `build.py` покрывают тесты: `make test`.
- **Те же проверки идут на каждый pull request** (`.github/workflows/ci.yml`): тесты, сборка и валидация контента. Если CI упал на `ОШИБКА ...` — это не формальность, а ровно тот случай, который иначе виден только на проде.
- `dist/` — сгенерированная директория, в git не коммитится (см. `.gitignore`).
